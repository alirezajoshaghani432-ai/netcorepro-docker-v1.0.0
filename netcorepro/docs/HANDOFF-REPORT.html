۱ خلاصهٔ مدیریتی

پروژه یک فروشگاه اینترنتی کامل و عملیاتی است که هم‌اکنون با دادهٔ واقعی در حال سرویس‌دهی است. تمام کد، پایگاه داده و تصاویر در این بسته قرار دارد و با سه دستور روی هر سرور لینوکسی مجهز به Docker بالا می‌آید. هیچ وابستگی به سرویس ابری یا CDN خارجی وجود ندارد.

۲ معماری سامانه

تصمیم‌های کلیدی طراحی

تصمیمدلیلپیامد عملی
رندر سمت سرور
SSR		 HTML آماده مستقیم از سرور ارسال می‌شود؛ بدون build سنگین سمت کلاینت و بدون هیدراسیون. اولین رنگ‌آمیزی بسیار سریع، ایندکس‌شدن کامل توسط موتور جستجو، و دیباگ ساده — کافی است «مشاهدهٔ منبع» بزنید.
SQLite
تک‌فایل		 حجم داده کوچک است و بار نوشتن پایین؛ یک پایگاه دادهٔ جدا صرفاً پیچیدگی اضافه می‌کرد. پشتیبان‌گیری یعنی کپی یک فایل. بدون سرویس جانبی، بدون تنظیم شبکه، بدون رمز اضافه.
ESM خوانا در dist/ کد نهایی مینیفای نشده و کامنت‌های توضیحی در آن باقی مانده است. برنامه‌نویس بعدی می‌تواند مستقیماً همین فایل‌ها را بخواند، ویرایش کند و سرویس را ری‌استارت کند.
دارایی‌های محلی
بدون CDN		 دسترسی به CDNهای خارجی از داخل ایران ناپایدار است. سایت در شبکهٔ کاملاً بسته هم بدون افت ظاهر بالا می‌آید. فونت و آیکون subset شده‌اند.
مذاکرهٔ WebP تصاویر محصول سنگین‌ترین بخش صفحه هستند. اگر مرورگر WebP بپذیرد، نسخهٔ سبک‌تر زیر همان URL سرو می‌شود؛ حدود ۶۵٪ صرفه‌جویی پهنای باند بدون تغییر مارک‌آپ.
tini به‌عنوان PID 1 Node در نقش PID 1 سیگنال‌ها را درست مدیریت نمی‌کند. با docker stop سیگنال SIGTERM به‌درستی می‌رسد و WAL پایگاه داده تمیز بسته می‌شود.
◆ دربارهٔ درایورهای MySQL و MSSQL

فایل‌های dist/db/mysql.js و dist/db/mssql.js در بسته وجود دارند اما مسیر پشتیبانی‌شده و آزمایش‌شده SQLite است. مقدار DB_TYPE را روی sqlite نگه دارید. مهاجرت به MySQL نیازمند بازنویسی لایهٔ پرس‌وجو است، چون کد از API همگام better-sqlite3 استفاده می‌کند.

الگوی رندر صفحه

هیچ موتور قالب جداگانه‌ای در کار نیست. هر صفحه یک تابع جاوااسکریپت است که رشتهٔ HTML برمی‌گرداند و از layout() مشترک برای هدر، فوتر و متا استفاده می‌کند. برای ویرایش ظاهر یک صفحه کافی است همان تابع را در views/ پیدا و تغییر دهید. 

// dist/views/site/pages.js — الگوی کلی هر صفحه
export function productPage(c, slug) {
  // ۱) خواندن داده به‌صورت همگام — بدون async/await
  const product = db.prepare(`SELECT … WHERE slug = ?`).get(slug);
  if (!product) return notFoundPage(c);

  // ۲) ساخت بدنهٔ صفحه با template literal
  const body = `<section class="nc-pdp"> … </section>`;

  // ۳) تحویل به چیدمان مشترک همراه با متای سئو
  return c.html(layout({
    title: product.seo_title || product.name,
    description: product.seo_description,
    body
  }));
}
⚠ نکتهٔ مهم هنگام ویرایش قالب

خروجی HTML باید همیشه از تابع esc() برای هر مقداری که از پایگاه داده می‌آید عبور کند. حذف این تابع مسیر تزریق اسکریپت (XSS) باز می‌کند. الگوی موجود در کد را دنبال کنید.

مهاجرت خودکار پایگاه داده

فایل dist/db/index.js در هر بار بالا آمدن سرویس، مجموعه‌ای از مهاجرت‌های idempotent را اجرا می‌کند: ستون‌های جدید در صورت نبود اضافه می‌شوند، ایندکس‌ها ساخته می‌شوند و بلوک‌های محتوایی پیش‌فرض تنها در صورت خالی بودن بخش درج می‌گردند. این یعنی می‌توانید یک پایگاه دادهٔ قدیمی را جایگزین کنید و سرویس خودش آن را به‌روز می‌کند — هیچ دستور مهاجرت دستی لازم نیست.

⚠ دو نکته که معمولاً باعث اشتباه می‌شود

یک: نام ستون رمز عبور password است، نه password_hash. هش با bcryptjs و ضریب ۱۰ ساخته می‌شود.

دو: پایگاه داده در حالت WAL کار می‌کند. کپی کردن صرفِ فایل .db بدون فایل‌های -wal و -shm منجر به از دست رفتن آخرین تراکنش‌ها می‌شود. همیشه از scripts/backup.sh استفاده کنید که با VACUUM INTO یک نسخهٔ یکپارچه می‌سازد.

◆ نکتهٔ امنیتی دربارهٔ کوکی و هدر

توکن هم در کوکی و هم در هدر Authorization پذیرفته می‌شود، اما کوکی فقط روی متدهای امن (GET/HEAD/OPTIONS) معتبر است. هر درخواست تغییردهنده (POST/PUT/DELETE/PATCH) الزاماً باید هدر Bearer بفرستد. این طراحی عمدی است و از حملهٔ CSRF جلوگیری می‌کند، چون یک سایت مهاجم نمی‌تواند هدر دلخواه روی دامنهٔ دیگر تنظیم کند.

۷ امنیت

لایه‌های پیاده‌سازی‌شده

لایهوضعیتتوضیح
هش رمز عبورفعال bcrypt با ضریب ۱۰. رمز خام هرگز ذخیره یا لاگ نمی‌شود.
توکن JWTفعال امضا با JWT_SECRET. تغییر این مقدار تمام نشست‌ها را باطل می‌کند.
کنترل دسترسی نقشیفعال سه سطح: authOptional · authRequired · adminRequired. تمام مسیرهای /admin/* در API بررسی نقش می‌شوند.
محافظت CSRFفعال کوکی فقط روی متدهای امن پذیرفته می‌شود؛ عملیات تغییردهنده هدر Bearer می‌خواهد.
تزریق SQLامن تمام پرس‌وجوها با prepare() و پارامتر مقید نوشته شده‌اند. کاراکترهای ویژهٔ LIKE نیز escape می‌شوند.
XSSامن هر مقدار پویا در قالب از تابع esc() عبور می‌کند.
اعتبارسنجی ورودیفعال Zod روی بدنهٔ تمام درخواست‌های نوشتنی. صفحه‌بندی نیز در برابر مقدار منفی و NaN مقاوم شده.
محدودسازی نرخفعال ۱۰ درخواست در دقیقه روی /api/auth/* بر پایهٔ IP. Nginx نیز لایهٔ دوم را اعمال می‌کند.
هدرهای امنیتیفعال secureHeaders در Hono: nosniff، frame options، referrer policy.
محدودیت حجم بدنهفعال پیش‌فرض ۱۰ مگابایت روی /api/*، قابل تنظیم با MAX_BODY_SIZE_MB.
اعتبارسنجی آپلودفعال فقط تصویر رستری پذیرفته می‌شود؛ SVG رد می‌شود تا مسیر XSS ذخیره‌شده بسته بماند.
کاربر غیر-rootفعال فرایند داخل کانتینر با UID 1001 اجرا می‌شود، نه root.
اعتبارسنجی کلید هنگام بوتفعال کانتینر با JWT_SECRET پیش‌فرض یا کوتاه‌تر از ۳۲ نویسه بالا نمی‌آید.
HTTPSدستی پیکربندی آماده در docker/nginx.conf، اما گواهی باید توسط تیم فنی نصب شود.
کد یک‌بارمصرف پیامکآزمایشی کد ثابت است و در پاسخ API برگردانده می‌شود. پیش از انتشار عمومی باید اصلاح شود.
⚠ سه اقدام امنیتی که قبل از باز کردن سایت به روی عموم الزامی است

۱. تولید JWT_SECRET تصادفی و اختصاصی همین سرور.
۲. تغییر رمز حساب مدیر از مقدار پیش‌فرض توسعه.
۳. اتصال سرویس پیامک واقعی و حذف کد ثابت — تا زمانی که این کار انجام نشده، هر کسی با دانستن کد ثابت می‌تواند با هر شماره‌ای وارد حساب مشتری شود.

⚠ دستور خطرناک

docker compose down -v علاوه بر توقف سرویس، تمام volumeها و در نتیجه کل پایگاه داده و تصاویر را پاک می‌کند. برای توقف معمولی همیشه از docker compose down بدون -v استفاده کنید.

۹ کارهای دستی — الزامی پیش از انتشار

این بخش مهم‌ترین قسمت سند است. هر مورد شامل شرح مسئله، محل دقیق آن در کد و راهکار پیشنهادی است. موارد قرمز پیش از باز کردن سایت به روی عموم باید انجام شوند.

۱ تولید کلید JWT اختصاصی بحرانی۲ دقیقه

کلید امضای توکن‌ها باید یک مقدار تصادفی و منحصربه‌فرد برای همین سرور باشد. کانتینر با مقدار پیش‌فرض یا کوتاه‌تر از ۳۲ نویسه اصلاً بالا نمی‌آید، اما این حفاظ را با یک مقدار ضعیفِ دلخواه هم می‌توان دور زد — پس حتماً از دستور زیر استفاده کنید.

پایگاه دادهٔ تحویلی با یک رمز توسعه‌ای و شناخته‌شده همراه است تا برنامه‌نویس بتواند بلافاصله پس از استقرار وارد پنل شود. این رمز باید در همان روز اول عوض شود.

۳ اتصال سرویس پیامک (پنل SMS) بحرانی۲ تا ۴ ساعت

وضعیت فعلی: ورود با شمارهٔ موبایل پیاده‌سازی شده و کار می‌کند، اما هیچ سرویس پیامکی متصل نیست. کد تأیید یک مقدار ثابت است و علاوه بر آن، در پاسخ API هم برگردانده می‌شود تا تست ممکن باشد.

خطر امنیتی

  • فعال کردن گزینه در پنل: /admin/settings ← مقدار pay_gateway_enabled را روی «فعال» بگذارید.
توجه به منطق موجود

در dist/api/orders.js خط ۶۰، گزینهٔ gateway تنها زمانی به فهرست روش‌های مجاز اضافه می‌شود که تنظیم pay_gateway_enabled برابر «فعال» باشد. بنابراین تا پیش از تکمیل پیاده‌سازی، این تنظیم را غیرفعال نگه دارید تا مشتری در فرایندی ناقص گرفتار نشود.

۵ دامنه، گواهی TLS و پروکسی معکوس مهم۱ تا ۲ ساعت

سایت هم‌اکنون روی پورت مستقیم و بدون رمزنگاری سرو می‌شود. برای انتشار عمومی باید پشت یک پروکسی با گواهی معتبر قرار گیرد. پیکربندی Nginx به‌صورت آماده در بسته موجود است و فقط باید فعال شود.

  • ثبت رکورد A دامنه روی آی‌پی سرور.
  • دریافت گواهی رایگان Let's Encrypt با certbot یا استفاده از گواهی سازمانی.
  • قرار دادن fullchain.pem و privkey.pem در پوشهٔ docker/certs/.
  • خارج کردن بلوک HTTPS و ریدایرکت از حالت کامنت در docker/nginx.conf.
  • تغییر انتشار پورت اپ به 127.0.0.1:8090:3000 تا مستقیماً از بیرون در دسترس نباشد.
  • اجرای docker compose --profile proxy up -d --build.
  • فعال کردن هدر Strict-Transport-Security پس از اطمینان از صحت گواهی.
  • تنظیم تمدید خودکار گواهی در cron.
# نمونهٔ دریافت گواهی و تمدید خودکار
certbot certonly --standalone -d netcorepro.ir -d www.netcorepro.ir

۶ بازبینی تنظیمات و اطلاعات تماس فروشگاه مهم۳۰ دقیقه

۴۵ کلید تنظیمات از پنل /admin/settings قابل ویرایش است و در سراسر سایت استفاده می‌شود. مقادیر فعلی مربوط به محیط قبلی است و باید با اطلاعات واقعی کسب‌وکار بازبینی شود.

⚠ شمارهٔ کارت بانکی

کلید pay_card_number در حال حاضر حاوی یک شمارهٔ کارت واقعی است که در صفحهٔ تسویه به مشتری نمایش داده می‌شود. پیش از انتشار حتماً بررسی کنید که این شماره متعلق به حساب درست کسب‌وکار باشد.

۷ فعال‌سازی پشتیبان‌گیری زمان‌بندی‌شده مهم۱۵ دقیقه

اسکریپت پشتیبان‌گیری آماده است و یک آرشیو یکپارچه شامل پایگاه داده و تمام تصاویر می‌سازد. فقط باید در cron ثبت شود. بدون این کار، از دست رفتن سرور به معنای از دست رفتن کل کاتالوگ و سوابق سفارش‌ها است. 

chmod +x /opt/netcorepro/scripts/*.sh
crontab -e

# پشتیبان روزانه ساعت ۳ بامداد، نگهداری ۱۴ روز
0 3 * * * cd /opt/netcorepro && ./scripts/backup.sh >> /var/log/ncp-backup.log 2>&1
  • حتماً یک نسخه از آرشیوها را به فضای خارج از همین سرور منتقل کنید (فضای ابری، سرور دوم یا دیسک جدا).
  • یک‌بار فرایند بازگردانی را روی محیط آزمایشی تمرین کنید: ./scripts/restore.sh <آرشیو> — در اجرای غیرتعاملی (cron) پرچم --yes الزامی است، وگرنه اسکریپت برای جلوگیری از بازگردانی ناخواسته متوقف می‌شود.
  • پشتیبانی که هرگز بازگردانی نشده، پشتیبان محسوب نمی‌شود.
۸ سخت‌سازی و پایش — توصیه‌شده اختیاری۱ تا ۳ ساعت
  • محدودسازی دسترسی پنل: اگر مدیران از آی‌پی ثابت کار می‌کنند، مسیر /admin را در Nginx با allow/deny محدود کنید.
  • پایش بیرونی: یک سرویس uptime روی /api/health تنظیم کنید تا قطعی سرویس بلافاصله اطلاع داده شود.
  • فایروال: با ufw فقط پورت‌های ۲۲، ۸۰ و ۴۴۳ را باز نگه دارید.
  • چرخش لاگ: در compose محدودیت اندازهٔ لاگ تنظیم شده (۱۰ مگابایت × ۵ فایل)؛ در صورت نیاز تغییر دهید.
  • محصول غیرفعال: محصول شمارهٔ ۱ (dlink-dwr-m921) در حال حاضر وضعیت inactive دارد و در فهرست عمومی دیده نمی‌شود. اگر باید به فروش برسد، از /admin/products فعالش کنید.
  • تنظیم منطقهٔ زمانی: مقدار TZ در .env روی Asia/Tehran است؛ در صورت نیاز تغییر دهید.

۱۰ نگهداری روزمره

دستورهای پرکاربرد

# وضعیت و سلامت سرویس
docker compose ps

# لاگ زنده
docker compose logs -f app
docker compose logs --tail=200 app

# ری‌استارت
docker compose restart app

# توقف (داده حفظ می‌شود)
docker compose down

# اعمال تغییر کد و بالا آوردن مجدد
docker compose up -d --build

# ورود به داخل کانتینر
docker exec -it netcorepro sh

اسکریپت‌های آماده

# تست دود روی تمام مسیرهای حیاتی
./scripts/healthcheck.sh
./scripts/healthcheck.sh https://netcorepro.ir

# پشتیبان کامل (دیتابیس + تصاویر)
./scripts/backup.sh
./scripts/backup.sh /mnt/backup

# بازگردانی از آرشیو (تأیید تعاملی می‌پرسد)
./scripts/restore.sh backups/netcorepro_backup_<تاریخ>.tar.gz

# بازگردانی بدون پرسش — برای cron یا اسکریپت
./scripts/restore.sh backups/netcorepro_backup_<تاریخ>.tar.gz --yes

# تغییر رمز مدیر
./scripts/reset-admin-password.sh 'رمز-جدید'

روند به‌روزرسانی کد

پشتیبان‌گیری← ویرایش فایل در dist/← docker compose up -d --build← ./scripts/healthcheck.sh← بررسی لاگ

چون کد به‌صورت ESM خوانا تحویل داده شده، هیچ مرحلهٔ کامپایل یا build جداگانه‌ای لازم نیست. فایل را ویرایش کنید و ایمیج را دوباره بسازید. برای تغییرات کوچک و آزمایشی می‌توانید فایل را مستقیماً داخل کانتینر کپی کرده و سرویس را ری‌استارت کنید، اما این تغییر با ساخت بعدی از بین می‌رود.

۱۱ عیب‌یابی

نشانهعلت محتملراه‌حل
کانتینر بلافاصله خارج می‌شود و لاگ می‌گوید JWT_SECRET نامعتبر است کلید هنوز مقدار پیش‌فرض دارد یا کوتاه‌تر از ۳۲ نویسه است دستور گام ۱ بخش ۹ را اجرا کنید و سپس docker compose up -d
خطای Could not locate the bindings file هنگام ساخت معماری پردازندهٔ سرور ARM است و باینری از پیش کامپایل‌شده سازگار نیست طبق هشدار بخش ۸، خط کپی باینری را حذف و اجازه دهید npm ماژول را کامپایل کند
سایت بالا می‌آید اما هیچ محصولی نمایش داده نمی‌شود volume دادهٔ خالی ساخته شده یا مسیر DB_PATH اشتباه است docker exec netcorepro ls -la /app/data — اگر فایل نبود، کانتینر را با volume خالی دوباره بسازید تا entrypoint دادهٔ اولیه را بازیابی کند
تصاویر محصولات نمایش داده نمی‌شوند (کادر خالی) volume تصاویر خالی است یا مسیر mount اشتباه است docker exec netcorepro ls /app/public/static/uploads | wc -l — باید حدود ۳۷۰ فایل باشد. در غیر این صورت از آخرین پشتیبان بازگردانی کنید
خطای database is locked دو فرایند هم‌زمان روی یک فایل SQLite می‌نویسند مطمئن شوید تنها یک کانتینر روی این volume اجرا می‌شود: docker ps | grep netcorepro
ورود مدیر با پیام «نام کاربری یا رمز اشتباه است» رد می‌شود رمز عوض شده یا حساب غیرفعال است ./scripts/reset-admin-password.sh 'رمز-جدید' — اسکریپت وضعیت حساب را هم به active برمی‌گرداند
پس از تغییر کلید JWT همه بیرون انداخته شده‌اند رفتار طبیعی است — امضای توکن‌های قدیمی دیگر معتبر نیست نیازی به اقدام نیست؛ کاربران دوباره وارد می‌شوند
خطای 413 هنگام آپلود تصویر از پنل حجم فایل از سقف مجاز بیشتر است مقدار MAX_BODY_SIZE_MB در .env و client_max_body_size در Nginx را افزایش دهید
پاسخ 429 روی صفحهٔ ورود محدودسازی نرخ فعال شده (۱۰ درخواست در دقیقه از هر IP) یک دقیقه صبر کنید. برای تغییر سقف، پارامتر rateLimit در dist/server.js را ویرایش کنید
پس از بازگردانی، داده‌ها قدیمی به نظر می‌رسند فایل‌های -wal و -shm قدیمی باقی مانده‌اند اسکریپت restore.sh این فایل‌ها را پاک می‌کند؛ اگر دستی بازگردانی کرده‌اید، آن‌ها را حذف و سرویس را ری‌استارت کنید
فونت فارسی یا آیکون‌ها نمایش داده نمی‌شوند مسیر /static/* توسط پروکسی درست هدایت نمی‌شود بررسی کنید هدر Accept در Nginx منتقل شود؛ حذف آن مذاکرهٔ WebP را هم خراب می‌کند
سرویس در حالت unhealthy می‌ماند اپ هنوز در حال راه‌اندازی است یا پایگاه داده پاسخ نمی‌دهد docker compose logs --tail=100 app و سپس curl -v localhost:8090/api/health
